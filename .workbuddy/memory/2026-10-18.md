## 实现要点（后续改动前必读）

- `SelectionCapacityServiceImpl#tryDeduct`：先 `getAuthoritativeCount`（DB COUNT）→ `alignSelectedCount`
  把 `teaching_class.selected_count` 对齐 DB → Lua 预扣 → 满员/漂移抛 `CLASS_CAPACITY_FULL` → Redis 异常走
  `degradeDeduct`（写 `SELECTION_DEGRADED_KEY` 后回落 DB 判定，不抛 5xx）。
- `executeRestore`（退课/补偿共用）：Redis 回补 + `teachingClassMapper.restoreSelectedCount` **同时**执行，
  所以 selected_count 不会只增不减。
- 选课主链路：`tryDeduct` → 注册事务回滚补偿（`afterCompletion` 非提交则 `compensateRestore`）
  → `updateSelectedCountWithCapacityCheck` 条件更新，返回 0 抛满员（真正的防超卖强制约束）。
- Lua 脚本返回值约定：`{1,count,capacity}` 成功 / `{0,...}` 满员 / `{-1,dbCount,capacity}` 漂移已校正。

## ⚠️ 已发现的并发缺口（未修，待架构师裁决 + W2 压测验证）

**递补路径只有第一道防线**：`WaitlistServiceImpl:285` `tryPromote` → `deductCapacity`（:549）只调
`selectionCapacityService.tryDeduct`，**没有** `updateSelectedCountWithCapacityCheck`。
而选课主链路（CourseSelectionServiceImpl）两道都有。
后果：递补落库后 DB count +1 但 `selected_count` 未 +1，直到下次 `alignSelectedCount` 才校正，
这中间存在并发超卖窗口。
建议修法（`WaitlistServiceImpl#deductCapacity` 内补）：
```java
int updatedRows = teachingClassMapper.updateSelectedCountWithCapacityCheck(teachingClassId, capacity);
if (updatedRows == 0) {
    selectionCapacityService.compensateRestore(teachingClassId);
    throw new BizException(ResultCodeEnum.CLASS_CAPACITY_FULL);
}
```
未擅自改的原因：递补属 V1.1 既有语义，改动需架构师拍板；且 W2 的并发压测会先暴露它。
