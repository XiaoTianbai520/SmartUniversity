## V1.1 六个任务全部完成

最终 `mvn -o -B clean compile -DskipTests` BUILD SUCCESS，214 个 java 文件，**无重复类名**（`find -printf "%f" | sort | uniq -d` 为空）。6 个智能体先后完成 T1~T6，文件归属矩阵完全守住，没有互相覆盖。

各模块落地要点：
- T2 候补：joinWaitlist 12 步校验、tryPromote 用队列快照单轮循环 + `promotedInRound` 标志保证收敛、退课后 Hook 触发。递补校验用**候补记录自身批次**的时间窗而非"当前进行中批次"（因 V1.0 withdrawCourse 只校验 dropDeadline，用后者会让批次结束后的退课误伤整队候补）。
- T3 通知：`@TransactionalEventListener(AFTER_COMMIT, fallbackExecution=true)` + 每接收人 `TransactionTemplate(PROPAGATION_REQUIRES_NEW)` 独立落库事务——注意 AFTER_COMMIT 阶段写库默认不在事务里，不套 REQUIRES_NEW 提交不了。
- T4 Excel：不用 EasyExcel 用 POI 5.4.1（离线已有）；`DataFormatter` 前加整数短路，否则 13 位学号被 POI 输出成科学计数法。
- T5 统计：不修改 ScoreMapper，复用 listScoreBySelectionIds 在内存聚合。

**两个踩坑 + 解法（后续迭代必看）**：
1. **COURSE_ADJUSTED 必须传 `bizId = null`**。因为 `uk_notice_dedup(notice_type, biz_id, receiver_user_id)` 会让同一教学班的第 2 次及以后调整通知被唯一键吞掉。MySQL 唯一索引对 NULL 不去重，传 null 才能"每次调整都通知"。同时 T3 监听器用 `isNull` 查重在 bizId 为 null 时会误判为"已存在"而跳过插入，**已改为 bizId != null 时才查重**。START/END、WAITLIST_PROMOTED、SCORE_PUBLISHED 仍带业务 ID 正常去重。
2. **容量上调触发递补不能同步调用 tryPromote**。tryPromote 是 PROPAGATION_REQUIRED，在 `saveTeachingClass` 事务内同步调用会让共享事务被标记 rollback-only，导致教务改容量整体回滚。改成 `TransactionSynchronizationManager` 注册 `afterCommit` 回调执行。退课场景不受影响（本就该同事务原子完成）。

未证实的部分：本机无 MySQL/Redis/RocketMQ，**未做运行时验证**，只过了编译 + 静态审查。`docs/V1.1_数据库增量设计.sql` 必须先执行，否则 waitlist_no/promoted_at 与 notification 表不存在。
