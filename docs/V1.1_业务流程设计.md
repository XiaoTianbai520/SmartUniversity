# 高校智慧教务选课平台 V1.1 业务流程设计

## 1. 文档说明

本文档描述 V1.1 业务增强版四个功能模块的可执行业务流程，是拆分开发任务、编写代码与验收的依据。

版本定位：**业务增强版**，在 V1.0 核心闭环之上补齐真实教务系统的辅助业务能力。

V1.1 的四条主线：

```text
候补选课 → 系统通知 → 批量导入导出 → 教师成绩统计
```

与 V1.0 的关系：

- V1.0 的规则（选课批次时间、专业年级权限、时间冲突、学分上限、容量校验）在 V1.1 **继续生效**；
- 候补学生被递补时必须**重新跑一遍 V1.0 的完整选课校验**，不允许因为"已经在候补队列里"就跳过校验；
- V1.0 接口行为保持兼容，V1.1 一律通过新增接口提供能力。

> 说明：`混合hlen` V1.0 中"课程人数已满"直接失败。V1.1 保留该行为，候补由学生显式发起。

# 2. 候补选课

## 2.1 状态模型

`course_selection.status` 由两种扩展为三种：

```text
SELECTED    已选（正式名额）
WAITING     候补中（占候补队列，不占正式名额）
WITHDRAWN   已退课 / 候补已取消 / 候补失效
```

状态流转：

```text
                 ┌────────── 退课 ──────────┐
                 ↓                          │
  （无记录）─选课─→ SELECTED ─退课/取消─→ WITHDRAWN
                 │                          ↑
                 │                          │
  （无记录）─候补─→ WAITING ──取消候补───────┤
                 │                          │
                 └──递补成功→ SELECTED       └──候补失效（重新校验不通过）
```

约束：同一学生、同一教学班在 `course_selection` 中**只能有一条记录**（唯一键 `uk_selection_student_class`），因此不可能出现"既已选又候补"。

## 2.2 加入候补

触发场景：学生在选课列表点击"加入候补"。

```text
学生点击加入候补
        ↓
身份校验（必须是 STUDENT，且 student 存在）
        ↓
教学班存在性校验 + 是否属于当前学期
        ↓
选课批次校验（存在进行中批次，且教学班在该批次开放范围内）
        ↓
专业权限校验
        ↓
年级权限校验
        ↓
重复校验（已存在 SELECTED → 重复选课；已存在 WAITING → 重复候补）
        ↓
时间冲突校验（与本人已选课程比较）
        ↓
学分上限校验
        ↓
容量校验：必须"已满"（SELECTED 人数 >= capacity）
        ↓ 未满时拒绝候补，提示直接选课
生成 waitlist_no = 该教学班当前最大候补序号 + 1
        ↓
写入 / 更新选课记录 status = WAITING
        ↓
返回候补位次
```

要点：

- **名额未满 deny 候补**。候补队列的存在意义是"名额争抢"，有空位时引导学生直接选课，避免队列与正式名额抢占混乱；
- 退课后重新候补时，`waitlist_no` 取当前最大值 + 1，即**不插队**；
- 候补不占用 Redis 容量计数，只在正式递补时扣减。

## 2.3 候补位次查询

```text
查询本人候补列表
        ↓
按 waitlist_no 升序返回
        ↓
位次 = (同一教学班内 waitlist_no 小于本人且状态为 WAITING 的记录数) + 1
        ↓
同时返回该教学班候补总人数、当前已选人数、容量
```

## 2.4 取消候补

```text
学生选择一条候补记录 → 取消
        ↓
校验归属：记录必须属于当前登录学生
        ↓
校验状态：必须为 WAITING
        ↓
校验时间：处于选课批次时间范围内（批次已结束时不允许变更）
        ↓
更新为 WITHDRAWN，waitlist_no 保留不清零
        ↓
后续候补同学的 waitlist_no 不做重排（序号允许断层）
```

> 为什么不用 SQL 重排：重排会在并发下产生行锁竞争且没有必要。位次通过"小于本人且 WAITING 的数量 + 1"实时计算，天然跳过已取消的记录。

## 2.5 候补递补（核心）

触发点有三个：

| 触发场景 | 触发位置 | 所属任务 |
|---|---|---|
| 正式选课学生退课释放出名额 | `CourseSelectionServiceImpl.withdrawCourse` | T2 |
| 教务上调教学班容量释放出名额 | `TeachingClassServiceImpl` 修改容量（**事务提交后回调**） | T6 |
| 教务手动触发递补 | 新增教务接口 | T2 |

统一调用新方法 `WaitlistService.tryPromote(teachingClassId)`。

> **为什么「教务上调容量」要走事务提交后回调**：`tryPromote` 自身的 `@Transactional` 是默认 `PROPAGATION_REQUIRED`，
> 若在教务修改教学班的事务内**同步**调用，它会加入同一个物理事务。一旦递补抛出未被其自身吞掉的异常，
> Spring 会把共享事务标记为 rollback-only，最终导致教务一个纯配置性质的「容量上调」连同本次变更一起回滚。
> 因此该场景改用 `TransactionSynchronizationManager` 注册 `afterCommit` 回调执行递补，
> 递补失败不再影响容量调整结果，教务可用手动触发接口兜底。
> 「退课触发」不受影响——退课与递补本就该在同一事务内完成，名额释放与占用必须原子。

流程：

```text
释放名额
   ↓
计算剩余可用名额 = capacity - COUNT(status = SELECTED)
   ↓
若 <= 0 → 直接结束
   ↓
取出候补队列第一条（status = WAITING，waitlist_no 最小）
   ↓
重新执行选课全部校验
   ├─ 批次状态、专业、年级、重复、时间冲突、学分上限
   ↓
   校验不通过？
   ├─ 是 → 该条标记为 WITHDRAWN（候补失效），continue 取下一条
   └─ 否 → status = SELECTED，记录 promoted_at，释放 waitlist_no 语义
            ↓
            扣减 Redis 容量计数（保持与 SELECTED 计数一致）
            ↓
            发布「候补递补成功」通知事件
            ↓
            继续尝试下一条，直到名额占满或队列清空
```

要点：

- 递补必须在**同一个事务**内完成，中途异常整体回滚；
- 退课带来的名额释放会被递补立即占用，因此**退课 + 递补后，教学班 SELECTED 人数不变**，Redis 计数先减后增，净值不变；
- 循环必须有终止条件：**单个名额最多尝试队列全部候补记录**，且只补足剩余可用名额，不允许无限循环；
- 候补失效记录落 `WITHDRAWN`，并在返回结构中体现，便于教务追溯。

## 2.6 我的课程中的候补展示

`StudentSelectionRespDTO` 中 `status` 字段本身使用 `SelectionStatusEnum.name()` 序列化，V1.1 会自动返回 `WAITING`。补充字段：

- `waitlistNo`：候补序号；
- `waitlistRank`：当前位次；
- `waitingCount`：该教学班候补总人数。

# 3. 系统通知

## 3.1 通知类型

```text
SELECTION_START     选课开始通知     → 面向有该批次选课资格的学生
SELECTION_END       选课结束提醒     → 面向有该批次选课资格的学生
WAITLIST_PROMOTED   候补成功通知     → 面向被递补的学生本人
COURSE_ADJUSTED     课程调整通知     → 面向该教学班已选学生
SCORE_PUBLISHED     成绩发布通知     → 面向该教学班已发布成绩的学生
```

## 3.2 数据模型

采用**一人一条**站内信模型：每条通知指向一个接收人，群发时批量插入多份。

好处：

- 未读数、标记已读、通知列表全部单表完成；
- 不需要"通知-用户关联表"与 дополнительные 已读记录表；
- 唯一键 `uk_notice_dedup(notice_type, biz_id, receiver_user_id)` 天然实现幂等。

## 3.3 通知产生流程

```text
业务模块发生事件
        ↓
调用 NoticeEventPublisher.publish(NoticeEvent)
        ↓
事件携带已解析好的接收人 user_id 列表
        ↓
事务提交后触发监听器（TransactionalEventListener, fallbackExecution = true）
        ↓
监听器为每个接收人构造 NotificationDO
        ↓
命中 uk_notice_dedup 的记录跳过（幂等）
        ↓
批量落库
```

为什么用事件解耦：

- 通知的产生方（候补、成绩、排课调整）不应该感知通知表结构；
- 事务失败时不应该发出通知（监听在事务提交后执行）；
- T6 集成时只需在各业务点埋一行 publish，不改动业务逻辑。

接收人解析通过 `NoticeTargetResolver` 完成，提供：

| 方法 | 用途 |
|---|---|
| `listUserIdsByRole(RoleEnum role)` | 全角色群发：选课开始 / 结束通知 |
| `listUserIdsByTeachingClassId(Long teachingClassId)` | 教学班维度：成绩发布、课程调整 |
| `listUserIdsBySelectionIds(List<Long> selectionIds)` | 选课记录维度：候补递补 |

## 3.4 通知消费

```text
学生 / 教师登录
        ↓
GET /api/v1/notifications/unread-count
        ↓
展示未读数量角标
        ↓
GET /api/v1/notifications       分页阅读通知列表
        ↓
PUT /api/v1/notifications/{id}/read     单条已读
PUT /api/v1/notifications/read-all      全部已读
```

权限要求：通知只能被接收人本人读取。查询时必须用当前登录用户的 `user_id` 过滤，**禁止**通过路径参数指定其他人。

## 3.5 幂等要求

- 监听器的插入必须幂等：事件重复投递时第二次插入会命中 `uk_notice_dedup`，捕获 `DataIntegrityViolationException` 后跳过；
- 批量插入时若部分命中唯一键，必须逐条降级为单条插入，保证不因个别重复导致整批失败；
- **`bizId` 为空的通知不做查重**。MySQL 唯一索引对 NULL 不去重，`COURSE_ADJUSTED` 一律传 `bizId = null`，
  语义是「每次课程调整都要通知学生」；此时监听器直接跳过查重逻辑，每次事件都落一条新通知。
  代价是同一事件重复投递会产生重复通知，可接受。其余四类通知（选课开始 / 结束、候补递补、成绩发布）
  都携带业务 ID，仍按 `uk_notice_dedup` 正常去重。

# 4. 批量导入导出

## 4.1 教务端：Excel 批量导入学生

```text
教务上传 xlsx
        ↓
校验：非空、文件后缀 .xlsx、非空工作表
        ↓
逐行读取：学号、姓名、专业编号、年级名称、班级编号、手机号（可选）
        ↓
逐行独立处理（单行失败不中断整体流程）
        ↓
行内校验：必填项、学号重复、专业/年级/班级是否存在且专业年级匹配
        ↓
调用已有 StudentService 新增学生，复用 V1.0 的账号创建逻辑
        ↓
汇总：总数 / 成功数 / 失败数 / 失败明细（行号 + 原因）
```

模板列：

| 列序 | 列名 | 必填 | 说明 |
|---|---|---|---|
| 1 | 学号 | 是 | 不可重复 |
| 2 | 姓名 | 是 | |
| 3 | 专业编号 | 是 | 关联 `major.major_code` |
| 4 | 年级名称 | 是 | 关联 `grade_cohort.grade_name` |
| 5 | 班级编号 | 是 | 关联 `academic_class.class_code` |
| 6 | 初始密码 | 否 | 缺省使用系统默认密码 |

处理原则：

- **逐行 try/catch，整体不放外层事务**。单行失败记录原因后继续，避免一个脏数据毁掉整个文件；
- 必须为每行新开事务边界，不能用外层大事务包裹，否则 StudentService 内部事务回滚会污染整个批次。

## 4.2 教务端：Excel 批量导入教师

同理，模板列：

| 列序 | 列名 | 必填 | 说明 |
|---|---|---|---|
| 1 | 教师编号 | 是 | 不可重复 |
| 2 | 姓名 | 是 | |
| 3 | 职称 | 否 | |
| 4 | 初始密码 | 否 | |

## 4.3 教务端：导出学生信息

```text
教务按现有分页查询条件筛选（专业/年级/班级/关键字）
        ↓
复用 StudentMapper.listStudentByCondition 查询（导出不限分页，设置合理上限）
        ↓
关联查询：专业名称、年级名称、班级名称
        ↓
生成 xlsx 并作为附件下载
        ↓
Content-Type: application/vnd.openxmlformats-officedocument.spreadsheetml.sheet
```

导出列：学号、姓名、专业、年级、班级、状态、账号状态。

## 4.4 教师端：导出教学班学生名单

```text
教师选择自己的教学班
        ↓
归属校验：教学班 teacher_id 必须等于当前登录教师
        ↓
查询该教学班 status = SELECTED 的选课记录
        ↓
关联学生：学号、姓名、专业、班级
        ↓
生成 xlsx 下载
```

## 4.5 教师端：Excel 批量导入成绩

```text
教师选择自己的教学班并上传 xlsx
        ↓
归属校验
        ↓
逐行读取：学号、姓名（校验用）、成绩
        ↓
行内校验：
   - 学号是否属于本教学班且状态为 SELECTED
   - 成绩是否在 0 ~ 100
   - 该记录成绩是否已发布（已发布拒绝覆盖）
        ↓
存在成绩记录则更新，不存在则插入
        ↓
汇总成功 / 失败明细
```

导入结果统一为 `ImportResultRespDTO`：

```text
totalCount    总行数
successCount  成功行数
failCount     失败行数
failList      失败明细：[{ rowIndex, identifier, reason }]
```

## 4.6 Excel 通用约定

- 依赖：**Apache POI 5.4.1**（本地仓库已离线可用，无需联网）；
- 只支持 `.xlsx`，`.xls` 直接拒绝并给出明确提示；
- 表头必须完全匹配模板，首行为表头，数据从第二行开始；
- 提供模板下载接口，模板与导入解析共用同一份列定义，避免两边漂移；
- 导入过程禁止引入 RocketMQ / Redis，保持同步执行，让教务立刻看到结果。

# 5. 教师成绩统计

## 5.1 统计口径

以**单个教学班**为统计单元。

```text
教师进入教学班详情
        ↓
归属校验（teacher_id = 当前登录教师）
        ↓
查询该教学班全部 status = SELECTED 的选课记录
        ↓
关联 score 表取已录入的成绩
        ↓
聚合计算
```

统计项：

| 指标 | 口径 |
|---|---|
| 统计人数 | 已录入成绩的记录数（不含未录入） |
| 未录入人数 | SELECTED 记录数 - 已录入成绩记录数 |
| 平均分 | 保留一位小数 |
| 最高分 | 数值原样保留 |
| 最低分 | 数值原样保留 |
| 及格率 | 成绩 >= 60 的人数 / 已录入人数 |
| 优秀率 | 成绩 >= 85 的人数 / 已录入人数 |
| 成绩分布 | 五段：<60、60-69、70-79、80-89、90-100，各段人数与占比 |

常量（定义在 Service 中）：

```text
PASS_SCORE_LINE  = 60
EXCELLENT_SCORE_LINE = 85
```

边界处理：

- 无已录入成绩时，人数为 0，平均分 / 最高分 / 最低分返回 0，比率返回 0，而不是报错或返回 null；
- 比率使用百分比并保留一位小数；
- 分母为 0 时必须返回 0，不允许除零异常。

## 5.2 为什么放在 Service 层聚合

- 数据量级在单个教学班（几十到几百条），内存中聚合完全够用；
- 避免为每个数据库方言写条件聚合 SQL；
- 后续 V2.0 需要做跨班级、跨学期的院系级分析时，再改为 SQL 聚合或走宽表。

# 6. 端到端演示流程

V1.1 完成后应能完整演示以下闭环：

### 候补链路

```text
教务创建容量较小的教学班并开启选课
        ↓
学生 A..N 选满该教学班
        ↓
学生 X 选课失败：课程人数已满
        ↓
学生 X 加入候补 → 返回候补位次
        ↓
学生 X 查看候补列表 → 看到位次与候补总人数
        ↓
学生 A 退课 → 释放名额
        ↓
系统自动递补：校验通过后把学生 X 转为正式选课
        ↓
学生 X 收到「候补成功通知」
        ↓
学生 X 在我的课表中看到该课程
```

### 通知链路

```text
教务开启选课批次
        ↓
定时任务扫描到批次开始 → 批量生成选课开始通知
        ↓
学生登录 → 未读数角标 +1
        ↓
学生点击通知 → 标记已读
```

```text
教师发布成绩
        ↓
事务提交后触发成绩发布通知
        ↓
该教学班学生收到成绩发布通知
```

### 导入导出链路

```text
教务下载学生导入模板 → 填写 → 上传导入 → 看到成功/失败明细
        ↓
教务按专业筛选 → 导出学生信息 xlsx
        ↓
教师进入自己的教学班 → 导出学生名单
        ↓
教师填写成绩 → 上传导入成绩 → 查看失败明细
        ↓
教师查看成绩统计 → 平均分/最高分/最低分/及格率/优秀率/分布
```
