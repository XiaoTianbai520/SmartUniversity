## 2. 场景 1：候补递补路径超卖窗口（已知缺口，重点）

### 2.1 结论
> **在 Redis 不可用（降级）场景下，候补递补路径存在真实并发超卖窗口；正常 Redis 模式下该窗口被 Lua 原子自增串行化所掩盖，但 `selected_count` 列在递补后不递增仍是隐患，依赖对账任务兜底。**

是否复现超卖：**代码层面可判定为「降级场景下会超卖」**；正常 Redis 模式下不会（被 Redis 互斥串行化）。本环境未做全量并发实测，故未给出超卖条数的实测值。

### 2.2 根因（逐行定位）
- 候补递补扣减容量方法 `WaitlistServiceImpl.deductCapacity`（`:549-555`）**仅调用 `selectionCapacityService.tryDeduct`**，缺少主链路同款的 `updateSelectedCountWithCapacityCheck` 第二道防线：

```java
// WaitlistServiceImpl.java:549（现状，缺第二道防线）
private void deductCapacity(Long teachingClassId, Integer capacity) {
    if (!redisDeductEnabled) {
        return;                       // ← 降级/关闭 Redis 时直接返回，无任何判定
    }
    selectionCapacityService.tryDeduct(teachingClassId, capacity);  // ← 唯一互斥，无 DB 条件更新
}
```

- 对照主链路 `CourseSelectionServiceImpl.deductCapacity`（`:411-427`）**同时具备两道防线**：

```java
// CourseSelectionServiceImpl.java:419-426（正确范式，主链路）
selectionCapacityService.tryDeduct(teachingClassId, capacity);   // 第 1 道：Redis Lua 原子预扣
registerCapacityCompensation(teachingClassId);
int updatedRows = teachingClassMapper.updateSelectedCountWithCapacityCheck(teachingClassId, capacity); // 第 2 道
if (updatedRows == 0) {
    throw new BizException(ResultCodeEnum.CLASS_CAPACITY_FULL);
}
```

- 超卖窗口触发条件：**Redis 降级**（`redis-deduct-enabled=true` 但 Redis 不可达，或 `redisDeductEnabled=false`）。
  - `tryDeduct` 内部捕获 Redis 异常后走 `degradeDeduct`（`SelectionCapacityServiceImpl:313-324`），其判定为
    `if (dbCount >= capacity) throw CLASS_CAPACITY_FULL; else return success` —— 该判定**读取 `dbCount` 与返回结果之间没有原子约束**（非 `SELECT ... FOR UPDATE`，也非条件 UPDATE）。
  - 两个并发递补线程同时读到 `dbCount = capacity-1`，都判定 `< capacity` 通过，随后都把候补记录 `status` 翻为 `SELECTED` → DB `COUNT(SELECTED)` 变为 `capacity+1`，**超卖 1 个名额**。
  - 由于 `deductCapacity` 缺少 `updateSelectedCountWithCapacityCheck`（`WHERE selected_count < capacity` 的原子条件 UPDATE + 行锁），候补路径没有 DB 层强制互斥，故窗口真实存在。
- 正常 Redis 模式下，`tryDeduct` 的 Lua 脚本对计数 Key 做**原子自增并校验**，并发递补被串行化，第一个自增到 `capacity` 后第二个直接返回满员，超卖被掩盖；但递补成功后 `selected_count` 列始终不 +1（缺第二道防线），需等对账/预热对齐前，若发生计数漂移仍存在隐患。

### 2.3 建议修法（仅文档化，未落地，待裁决 #1）
在 `WaitlistServiceImpl.deductCapacity` 补上第二道防线，与主链路对齐：

```java
// WaitlistServiceImpl.java —— 建议补丁（未落地，待架构师裁决 #1）
private void deductCapacity(Long teachingClassId, Integer capacity) {
    if (!redisDeductEnabled) {
        // 降级/关闭 Redis：直接以 DB 条件更新为唯一互斥，避免非原子 dbCount 判定
        int updated = teachingClassMapper.updateSelectedCountWithCapacityCheck(teachingClassId, capacity);
        if (updated == 0) {
            throw new BizException(ResultCodeEnum.CLASS_CAPACITY_FULL);
        }
        return;
    }
    // 第 1 道：Redis Lua 原子预扣
    selectionCapacityService.tryDeduct(teachingClassId, capacity);
    // 第 2 道：DB 条件更新，真正防止并发超卖（与选课主链路一致）
    int updated = teachingClassMapper.updateSelectedCountWithCapacityCheck(teachingClassId, capacity);
    if (updated == 0) {
        selectionCapacityService.compensateRestore(teachingClassId); // 回补 Redis 预扣
        throw new BizException(ResultCodeEnum.CLASS_CAPACITY_FULL);
    }
}
```

> 说明：`updateSelectedCountWithCapacityCheck`（`TeachingClassMapper:135`，已冻结文件内既有方法）与 `compensateRestore`（`SelectionCapacityService` 既有方法）均已存在，补丁**不新增任何 Mapper default 方法、不新增 XML、不修改冻结文件**，仅调整 `WaitlistServiceImpl` 内部实现。是否落地以架构师裁决 #1 为准，本工作流（W2）**不改该代码**。

## 3. 场景 2：主链路并发抢最后 1 名额（100 / 500 / 1000）

- **是否超卖：否。** 主链路具备双保险（§2.2 已列）：Redis Lua 原子预扣 + `updateSelectedCountWithCapacityCheck` DB 条件更新（`selected_count < capacity` 行锁，唯一真正防超卖的强制约束）。即便 Redis 降级，`updateSelectedCountWithCapacityCheck` 的 InnoDB 行锁仍保证只有一个事务能成功自增，其余返回 `40910 课程容量已满`。
- **最终成功人数：恰好 1 人。**
- **成功率**：理论为 `1/N`（N 为并发数），其余 `N-1` 请求返回 `40910`。
- **平均响应时间**：未实测；推断正常负载个位数~数十 ms。1000 并发下，落败请求因争抢同一教学班行锁而延迟上升（先阻塞后失败），但仍在秒级内，需实测确认峰值。
- **数据库连接数 / Redis 请求情况**：服务端指标，未实测；并发 1000 时务必确认 Hikari 连接池上限（`maximum-pool-size` 默认 10）与 Redis 连接池是否够用，否则会出现连接获取等待/超时（非超卖，而是吞吐受限）。

## 4. 场景 3：同一学生并发重复选同一教学班

- **是否重复选课：否。** 选课主链路在 `tryDeduct` 之前已做重复选课前置校验（`getSelectionByStudentAndClass` 查重，命中抛 `40909 重复选课`），且 `course_selection` 存在 `(student_id, teaching_class_id, status)` 维度唯一约束兜底。同一学生并发重复选同一教学班，只有一个线程能先落库成功，其余返回 `40909`。
- **最终成功条数：恰好 1 条。**
- **成功率**：理论 `1/N`，其余 `N-1` 返回 `40909`。
- 响应时间 / 连接数 / Redis：同场景 2 口径，未实测。

## 5. 场景 4：Redis 不可用降级路径

- **是否抛 5xx：否。** 容量服务 `tryDeduct` 内部对所有 Redis 异常 `catch` 后走 `degradeDeduct`（`SelectionCapacityServiceImpl:313-324`）：写 `SELECTION_DEGRADED_KEY` 标记降级，再按 `dbCount >= capacity` 回落 DB 判定，返回业务结果（`2xx` 或 `4xx CLASS_CAPACITY_FULL`），**不向上抛 5xx**。
- 主链路在 `tryDeduct`（已降级）之后仍执行 `updateSelectedCountWithCapacityCheck`（纯 DB 操作，不依赖 Redis），因此降级时主链路仍由 DB 条件更新保护，**不超卖、不 5xx**。
- 候补递补路径在降级场景下的超卖窗口见 §2；本场景重点验证「不抛 5xx」，结论成立。
- 压测方式：运维先停 Redis，再以 `--mode degrade` 运行脚本，确认响应状态码无 `>=500`。正常 Redis 模式下该场景仅验证接口可用性，降级语义需 Redis 实际宕机才触发。

## 6. 压测脚本使用说明（W2-3）

脚本：`scripts/stress/selection_stress.py`（纯标准库，无需 `pip install`）。四个模式：

```bash
# 主链路抢最后 1 名额（教学班 10，100 并发，学生 20260001~20260100）
python scripts/stress/selection_stress.py --mode main --teaching-class-id 10 --threads 100 \
    --student-prefix 20260 --student-start 1 --student-count 100 --student-pass 123456

# 重复选课（学生 20260001 并发 50 次选教学班 11）
python scripts/stress/selection_stress.py --mode duplicate --teaching-class-id 11 --threads 50 \
    --student 20260001 --student-pass 123456

# 候补超卖窗口（教学班已满，500 并发选）
python scripts/stress/selection_stress.py --mode waitlist --teaching-class-id 12 --threads 500 \
    --student-prefix 20260 --student-start 1 --student-count 500 --student-pass 123456

# 降级路径（先停 Redis，再并发选课验证无 5xx）
python scripts/stress/selection_stress.py --mode degrade --teaching-class-id 13 --threads 100 \
    --student-prefix 20260 --student-start 1 --student-count 100 --student-pass 123456
```

脚本输出：每个请求的 `http_status / code / latency_ms / success`，并在结尾汇总 **成功率、平均/最小/最大响应时间、HTTP 5xx 数、是否超卖（API 层成功数 > 容量）、是否重复选课（同学生成功 > 1）、状态码分布**，以及「数据库连接数 / Redis 请求情况」的服务端采集提示。可用 `--out` 落盘 JSON 便于二次分析。

> 目标学期需处于选课窗口（IN_PROGRESS 批次）。若当前学期无进行中批次，可加 `--flip-semester-id <id>` 将另一学期临时置 `PLANNED`（脚本 `finally` 中恢复为 `ACTIVE`），与 `target/smoke_selection.py` 手法一致。
